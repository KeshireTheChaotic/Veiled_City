## TOK06 — cancellation, retry and usage truth

`GMService.requestModel` checks the shared operation signal before dispatch and again after receiving a response. An expired operation cannot return a late candidate for native preview/commit. Pre-cancelled work is **zero dispatches**, not a fabricated provider request. A response actually returned after cancellation records its **reported** input/output/cached usage once as a failed request, then throws `AI_GENERATION_DEADLINE`. Missing usage stays unknown; cancellation is not evidence that the server spent no tokens or charged nothing.

Preserved bounded app retries, `maxRetries:0` on every SDK request, two structured JSON attempts, shared router/GM deadlines and recovery guards. Backoff is abortable. Valid seconds/date `Retry-After` hints are never shortened: within the existing one-second bounded-wait ceiling, wait at least the hint; longer hints propagate the original error for safe deferred recovery rather than retrying early. No header/prompt/private JSON enters telemetry. Existing error/turn notices continue to distinguish no commit from committed/uncertain recovery; no native replay or blind Discord resend is introduced.

Official OpenAI documentation informed the retry audit: [rate-limit guidance](https://developers.openai.com/api/docs/guides/rate-limits) recommends avoiding nested SDK/application retry multiplication, bounding retry time, and not retrying earlier than valid server hints. Installed `openai/client.mjs` was inspected read-only: it accepts per-request retry limits and checks abort state. No SDK upgrade, API key/credential inspection, live provider or cancellation endpoint call. The application guards are defense-in-depth and deterministic adapter-contract tests, not a claim that the installed SDK previously dispatched every aborted request. The transport must honor its abort/timeout contract; this phase does not forcibly terminate an arbitrary replacement transport that never settles or guarantee server-side billing cancellation.
