# R6/R7 verified native runtime resume — implementation slice complete

Native startup now supports explicit VK2_RESUME=1 for a preserved native directory instead of requiring deletion or a new state namespace. Existing VK2_NATIVE, single-guild and inference opt-ins remain required. New directories receive a dedicated runtime.sqlite manifest. Startup binds run identity, exact guild, canonical read-only source path/content (including present WAL/journal), physical native file identities and table/index/trigger schema hashes. Missing stores, unknown files, changed source/guild/version/schema and foreign/replaced state require review before another repository/root/client is opened. Existing game rows are neither imported nor backfilled by this boundary.

The metadata connection uses SQLite EXCLUSIVE locking mode and a process-lifetime exclusive transaction. It retains its lock across manifest commits and releases it on close/crash, so a second instance of this startup entry point cannot open the same directory. The lock is per directory, not a global per-guild lease across unrelated directories or a fence against trusted code bypassing startNative. This matches the [SQLite locking-mode contract](https://www.sqlite.org/pragma.html#pragma_locking_mode) and was exercised with two connections and an actual owned child-process kill. No PID guessing, timed lease, heartbeat or file-delete recovery.

A new manifest is durably initializing before root construction and ready before login. Pure provider-init failure can retry with explicit resume if no game stores were created. Partial root initialization with unmanifested game stores remains held for reviewed migration; no empty-state repair. Old pre-manifest directories are refused without creating a manifest or erasing old state. Adding inference's dedicated empty stores is an explicit opt-in; existing known stores must retain their identities/schemas. Cleanup releases repository/client/runtime resources after failure and on one idempotent close.
