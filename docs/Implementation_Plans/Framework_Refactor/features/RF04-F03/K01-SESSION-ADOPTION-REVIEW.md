# Personal owner reader — Session adoption review

The supported bot start in `bot/package.json` executes `src/index.js`; `initializeKnowledgeSession()` is called before configuration, database construction and runtime service creation. Session's `sessionBrief` is called from command and story-command handlers. `captureDialogue` and `prepareSceneEntry` are reached through authored candidates; typed intents also invoke dialogue capture. `resolveMundaneEntry` and `suggestSetupPayoff` are reached from AI intent dispatch. The registration CLI builds commands and the export CLI reads campaign data; inspected entrypoints do not invoke these five readers. The package is private and the inspected setup documentation does not advertise a standalone Session module API.

The five Session root files presently import the original `personal-continuity.js` reader. Its owner/attendance check works without application composition. An initialization-bound Session port would therefore change direct pre-bootstrap invocation. Specifically, `captureDialogue` and `entryReferenceContext` catch errors from this reader and can return null, so an uncomposed call could appear as absent speech or entry context instead of an explicit composition error. The production bot startup supplies an initializer, but the direct-call behavior has not been shown safe to remove. Do not claim saved-reader compatibility from startup ordering alone. K01 keeps the root reader and its pre-bootstrap check unchanged.

A later adoption needs an exact compatibility design, or an evidence-backed boundary for each supported entrypoint, plus fresh tests of the current owner, assignment, attendance and source behavior. The failed or ambiguous path is local to these callers; unrelated migration may continue. No runtime or test was run for this documentation review. RELEASE NOT AUTHORIZED.
